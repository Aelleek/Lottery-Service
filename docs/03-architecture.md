# 03 구조

## 1. 전체 구성

- Spring Boot 3, Java 17 단일 애플리케이션과 MySQL 8.4를 쓴다. 별도 메시지 서버나 마이크로서비스는 두지 않는다. 번호 저장과 "이어서 할 일"을 같은 DB 트랜잭션에 함께 저장할 수 있기 때문이다.
- 비동기 처리는 같은 애플리케이션 안의 worker가 맡는다. 인스턴스를 여러 개 띄워도 job lease로 같은 일을 두 번 처리하지 않는다(4절).
- 첫 출시 운영은 인스턴스 1개를 가정한다. 비회원 자격 발급 속도 제한처럼 메모리에 두는 것은 인스턴스를 늘릴 때 DB로 옮긴다.
- 스키마는 Flyway 같은 버전형 migration으로 관리한다. 잠금과 유일성 검증은 H2가 아니라 실제 MySQL로 테스트한다.
- 로컬 `docker-compose.yml`은 아직 `mysql:8.0`이다. 설계 기준인 8.4와 맞춘다.
- 화면 기술은 아직 정하지 않았다. 지금은 정적 HTML(`src/main/resources/static/index.html`)이 API를 호출한다. 이전 설계 초안은 Thymeleaf를 가정했다.

## 2. 패키지

레이어가 아니라 기능 단위로 나눈다. 현재 코드의 `lotto`, `member`, `auth`를 아래처럼 나눠 간다.

| 패키지 | 맡는 일 | 현재 코드에서 오는 것 |
|---|---|---|
| `round` | 회차 일정, 판매 마감 봉인, 현재 회차 계산 | `LottoService`의 고정 회차 1112 |
| `recommendation` | 무작위 생성, 생성 필터, 조건 검증, 추천 저장 | `LottoService.recommendAndSave*`, `lotto/validation` |
| `record` | 기록, 구매 등록·취소, 내역 조회, 비회원 가져오기 | `LottoRecord`, `addPurchasedRecords` |
| `result` | 공식 결과 수집·검증·게시, 판정, 즉시 확인 | `DhlotteryClient`, `LottoWinnerSyncService` |
| `notification` | 연락처 인증, 동의, 알림 대상, 발송 슬롯, 제공자 상태 조회 대조, 예산 | 없음 |
| `account` | 회원, 소셜 계정, 비회원 자격, 귀속, 세션, 탈퇴 | `member`, `auth` |
| `stats` | 활동 이벤트, 집계, 기간별 고유 이용자 | 없음 |
| `admin` | 관리자 권한·감사, 수동 다시 보내기, 결과 승인과 직접 등록, 통계 조회 | 없음 |
| `common` | 명령 토큰, 멱등 처리, job과 worker, 시계(Clock), 오류 형식, 운영자 알림 발송 | 없음 |

탈퇴 삭제 job은 `account`가 맡는다. [04 6.2](04-data.md#62-탈퇴할-때)의 순서를 그대로 지켜야 하므로, 사건을 뿌려 각 패키지가 알아서 지우게 하지 않고 `account`가 각 패키지의 삭제 기능을 그 순서대로 직접 부른다 **[미확인]**. 다른 패키지의 테이블을 직접 다루지는 않는다.

생성 필터는 현재 구조를 유지한다. `LottoValidationRule` 빈을 `@Order` 순서로 모아 첫 실패에서 멈추는 파이프라인이다. 바뀌는 점은 두 가지다.

- 회원과 비회원 추천이 같은 생성기를 쓴다.
- 과거 1등 필터의 비교 자료를 바꾼다. 지금은 앱 시작 때 한 번 읽은 목록(`LottoWinnerDataCache`)을 계속 쓴다. 바뀐 뒤에는 결과가 게시될 때마다 갱신하고, 추천 회차보다 앞선 회차만 비교한다. 관리자 실험이 과거 회차를 다시 계산할 때도 같은 규칙으로 그 회차 이전 결과만 쓴다.

- 외부 호출은 DB 트랜잭션 밖에서 한다. 응답을 받은 뒤 짧은 트랜잭션으로 저장한다.
- 결과 API 응답은 크기, 회차, 번호 범위, 중복, 보너스를 검증한 뒤에만 게시한다. HTTP 200이어도 로그인 화면 HTML이나 다른 회차가 오면 실패로 본다.

## 4. 비동기 처리

예를 들어 결과를 게시하면 회원마다 등수를 판정해야 한다. 이 판정을 게시와 같은 요청 안에서 다 하면 오래 걸리고, 중간에 서버가 꺼지면 어디까지 했는지 모른다. 그래서 두 가지 장치를 쓴다(C-28).

1. **같은 트랜잭션에서 job 등록.** 결과 게시 트랜잭션 안에서 판정 job 행을 함께 넣는다. 게시가 rollback되면 job도 사라지고, 커밋되면 job이 반드시 남는다. 이어서 할 일이 여럿이면 job을 여럿 넣는다. 별도 outbox 테이블은 두지 않는다.
2. **job과 lease.** worker는 job을 가져갈 때 일정 시간 유효한 처리 권한(lease)과 토큰을 받는다. 저장할 때마다 토큰이 아직 자기 것인지 확인한다. 권한이 만료된 늦은 worker의 저장은 거부된다. 오래 걸리는 job(판정, 탈퇴 삭제)은 진행 위치를 `cursor_json`에 남겨 이어서 한다.

모든 job은 다시 실행해도 결과가 같아야 한다. 같은 job이 두 번 돌아도 효과가 한 번만 남도록, 결과를 쓰는 테이블의 유일 제약(예: 판정은 기록·게시본·기록 버전당 하나)이나 덮어쓰기(예: 집계는 원천에서 다시 계산한 값으로 덮어쓴다)로 막는다. 같은 일을 두 번 등록하지 않도록 job에는 (종류, 중복 키) 유일 제약이 있다.

외부 발송은 이 장치로도 중복을 완전히 막지 못한다. 제공자 호출 뒤 응답을 못 받으면 접수 여부를 알 수 없기 때문이다. 그래서 발송은 별도로 UNKNOWN 상태와 대조 절차를 둔다([05 8](05-flows.md#8-알림-발송)).

worker가 처리 중에 죽으면 lease가 만료된 채 RUNNING으로 남는다. 회수 worker가 이런 job을 찾아 시도 횟수를 늘리고 RETRY_WAIT로 돌린다. 시도 상한을 넘기면 DEAD로 두고 운영자에게 알린다 **[미확인]**. 주기와 상한은 [07 1](07-operations.md#1-작업-일정)에 있다. 발송 슬롯 job을 회수하면 그 job의 IN_FLIGHT 메시지는 다시 호출하지 않고 UNKNOWN으로 바꿔 대조한다([05 8.3](05-flows.md#83-접수-여부를-모를-때)).

job 큐에서 다음 일을 고를 때만 `SKIP LOCKED`를 쓴다. 추천 중복 검사나 마감 대상 열거에서는 잠긴 행을 건너뛰면 안 되므로 쓰지 않는다.

## 6. 보안

서비스를 연 뒤 외부의 악의적인 공격에 대처할 수 있어야 한다. 이 절은 앱이 지키는 규칙이다. 서버와 네트워크처럼 호스팅에 따라 달라지는 것은 [07 5](07-operations.md#5-출시-조건)의 출시 조건으로 정하고, 사고가 났을 때 할 일은 [07 7](07-operations.md#7-보안-사고-대응)에 있다. 기능을 만드는 단계에서 이 절의 항목을 함께 구현한다([08 2](08-delivery.md#2-구현-순서)).

### 6.1 공통 규칙

- 요청 본문의 회원 ID나 주체 ID를 믿지 않는다. 세션이나 비회원 쿠키에서 주체를 구한다.
- 다른 회원의 자원은 존재 여부도 알 수 없게 404로 답한다.
- 쿠키로 인증하므로 변경 요청에 CSRF 방어를 켠다. 토큰은 비회원 자격이나 회원 세션에 묶어 서버가 서명한 값이고, 응답 본문으로 준다. 서버에는 저장하지 않는다(D-051). 지금 꺼져 있는 CSRF는 첫 출시 전에 켠다.
- 로그, 통계 이벤트, 오류 응답, 예외 메시지에 번호 조합, 전화번호, 인증 코드, 토큰, 키 원문을 남기지 않는다.
- 시각은 주입한 `Clock`으로 다룬다. 마감 판단처럼 경계가 중요한 시각은 DB에서 다시 읽는다([05 2](05-flows.md#2-추천)).
- 관리자 기능은 6.3을 따른다.

### 6.2 전송, 쿠키, 응답 헤더

- 운영은 HTTPS로만 받는다. http 요청은 https로 보낸다. HSTS는 `max-age=31536000; includeSubDomains`이고, preload 등록은 도메인을 정한 뒤 정한다 **[미확인]**.
- 회원 세션 쿠키와 비회원 쿠키는 `Secure`, `HttpOnly`, `SameSite=Lax`다. `secure: false`는 local 프로필에서만 쓴다. 소셜 로그인 콜백은 제공자에서 돌아오는 페이지 이동이라 `Strict`로는 세션 쿠키가 붙지 않는다.
- 모든 응답에 아래 헤더를 붙인다(C-29).

| 헤더 | 값 | 막는 것 |
|---|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'` | 끼워 넣은 스크립트 실행, 다른 사이트가 우리 화면을 틀 안에 넣어 클릭을 훔치는 것 |
| `X-Frame-Options` | `DENY` | 위와 같음. 오래된 브라우저용 |
| `X-Content-Type-Options` | `nosniff` | 브라우저가 파일 종류를 추측해 스크립트로 실행하는 것 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 다른 사이트로 이동할 때 주소의 경로·검색어가 넘어가는 것 |
| `Permissions-Policy` | `camera=(self), microphone=(), geolocation=()` | 쓰지 않는 기기 권한 요청. 카메라는 QR 입력(단계 7) 때문에 우리 사이트에만 허용 |
| `Cache-Control` | 개인 자료를 담은 API 응답은 `no-store` | 공용 PC나 중간 캐시에 남는 것 |

- CSP는 인라인 스크립트·스타일을 쓰지 않는 것을 전제로 한다. 화면 기술을 정하면 다시 본다([08 6](08-delivery.md#6-남은-설계-작업)).
- 오류 응답에는 스택, 프레임워크 버전, SQL을 싣지 않는다. 원인은 `requestId`로 서버 로그에서 찾는다.
- 운영에서 열지 않는 것: H2 콘솔, 개발·테스트용 경로, 외부에서 닿는 관리 엔드포인트(Actuator를 쓰면 health만 내부에서), API 문서 화면.
- 다른 출처(CORS)는 허용하지 않는다. 변경 요청의 출처 검사는 [05 1](05-flows.md#1-비회원-자격-발급)과 같다.

### 6.3 인증과 관리자

- 로그인은 소셜 로그인만 쓴다. 비밀번호를 저장하지 않는다.
- 로그인에 성공하면 세션 ID를 새로 만든다. 로그인 전 세션을 이어 쓰게 하는 공격(세션 고정)을 막는다.
- 재인증(C-31). 민감한 작업([02 7.2](02-policies.md#72-회원-계정)) 전에 제공자 로그인을 다시 거치게 한다. 제공자에게 로그인 화면을 다시 띄우라고 요청한다(예: 구글 `prompt=login`, 카카오 `prompt=login`, 네이버 `auth_type=reauthenticate`) **[미확인]**.
  - 돌아온 계정의 (제공자, 제공자 사용자 ID)가 세션의 회원에 연결된 계정과 같을 때만 성공이다. 다른 계정으로 재인증하면 거부한다.
  - 성공하면 재인증 시각을 서버 세션에 적고, 민감한 API는 그 시각이 5분 안인지 본다. 증명을 화면에 넘기지 않아 주소나 로그로 새지 않는다. 그래서 openapi의 `X-Reauthentication-Proof` 헤더는 재인증을 구현하는 단위에서 뺀다.
  - 재인증이 실패하거나 취소되면 그 작업만 403으로 거부하고 세션은 유지한다.
- 관리자 다중 요소 인증은 인증 앱 코드(TOTP)다(D-047).
  - 30초 단위 6자리 코드(RFC 6238). 기기 시계 차이를 위해 앞뒤 한 단위까지 받는다.
  - 관리자 세션을 시작할 때마다 확인한다. 결과 직접 등록처럼 위험한 변경은 여기에 더해 최근 5분 재인증이 필요하다([02 5](02-policies.md#5-결과와-판정)).
  - 앱 비밀값은 연락처와 같은 방식으로 키 버전과 함께 암호화해 저장한다. 마지막으로 받은 시간 단위를 저장해 같은 코드를 다시 받지 않는다.
  - 5번 틀리면 15분 잠그고 운영자에게 알린다 **[미확인]**.
  - 처음 등록할 때 복구 코드 10개를 한 번만 보여 준다. 코드마다 한 번만 쓸 수 있고 해시로만 저장한다.
  - 저장할 자리는 `admin_grant`의 컬럼(암호문, 키 버전, 마지막 시간 단위, 실패 수, 잠금 시각, 복구 코드 해시)이다. `schema.sql`에는 관리자 인증을 구현하는 단위에서 V1과 함께 넣는다.
- 관리자 권한 부여(C-33). 첫 ADMIN은 운영 책임자가 서버 관리 명령으로 부여한다. 그 뒤에는 ADMIN이 화면에서 부여·회수하고, 사유와 함께 감사 기록에 남긴다. 2차 인증을 초기화할 때(기기 분실, 복구 코드 소진)도 같다. ADMIN이 한 명뿐이면 관리 명령으로 한다.
- 같은 브라우저의 일반 로그아웃은 그 세션만 서버에서 지운다. 다른 기기의 세션은 그대로 둔다.
- 다른 기기 로그아웃(최근 5분 재인증 필요), 탈퇴, 사고 대응은 `member.auth_version`을 올린다. 버전이 다른 세션은 요청마다 거부한다. 사고 때 모든 세션을 회수하는 방법은 [07 7](07-operations.md#7-보안-사고-대응)에 있다.

### 6.4 입력과 출력

- 모든 입력은 서버에서 검사한다. 범위, 길이, 형식, 목록 개수다. 화면의 검사는 편의일 뿐이다.
- 요청 본문은 64KB를 넘으면 받지 않는다 **[미확인]**. 목록을 받는 API(구매 등록, 즉시 확인 등)는 openapi의 개수 상한을 넘으면 400이다.
- DB 쿼리에는 값을 매개변수로만 넘긴다. 정렬처럼 이름을 고르는 값은 허용 목록에서 고른다. 문자열을 이어 붙여 SQL을 만들지 않는다.
- 사용자 입력과 외부 응답을 화면에 넣을 때는 텍스트로 넣는다. 예를 들어 `innerHTML` 대신 `textContent`를 쓰고, 서버 렌더링이면 자동 이스케이프를 끄지 않는다. 화면 기술을 정하면 다시 정한다.
- 외부 응답(결과 API, SOLAPI)을 믿지 않는다. 크기 상한과 형식 검증을 거친다(3절). 외부 호출에는 연결·응답 시간 제한을 둔다.

### 6.5 요청 제한

| 대상 | 기준 | 한도 | 근거 |
|---|---|---|---|
| 비회원 자격 발급 | IP | 10분에 200회 | D-035 |
| 추천 생성 | 주체 | 동시에 1개, 최소 1초 간격 | [02 2.1](02-policies.md#21-기본-규칙) |
| 인증 코드 | 번호, 계정 | 재발급 60초, 하루 5회, 오답 5회 | [02 6.4](02-policies.md#64-수신-번호와-동의) |
| 현재 회차, 회차 결과 조회 | IP | 1분에 120회 | D-048 |
| 즉시 확인 | IP | 1분에 30회 | D-048 |
| 로그인 시작 | IP | 1분에 20회 | D-048 |
| 모든 API 합계(로그인 사용자 포함) | IP | 1분에 300회 | D-048 |

- 넘으면 429와 `Retry-After`를 준다. 화면은 다시 시도할 수 있는 시각을 보여 준다.
- 값은 초기 설정이다. 부하 시험 뒤 조정한다(D-020).
- 첫 출시는 인스턴스 1개라 메모리에서 센다. 인스턴스를 늘릴 때 DB로 옮긴다(1절).
- 앞단(프록시나 CDN) 뒤에서는 IP를 그 앞단이 붙인 헤더에서만 읽는다. 사용자가 보낸 `X-Forwarded-For`를 그대로 믿으면 한도를 우회할 수 있다.
- 수많은 IP에서 한꺼번에 오는 대규모 공격은 앱이 막지 못한다. 앞단 보호 방식은 호스팅과 함께 정한다(D-049, [07 5](07-operations.md#5-출시-조건)).

### 6.6 비밀값과 키

- 파일 구성은 5절과 같다. 운영 서버에서 비밀값을 둘 곳과 권한은 호스팅과 함께 정한다([07 5](07-operations.md#5-출시-조건)). 앱 실행 계정만 읽을 수 있게 한다.
- 키마다 버전을 둔다(C-30). 새 값은 현재 버전으로 서명·암호화하고, 확인은 남아 있는 모든 버전으로 한다.
  - 교체: 새 버전을 더하고 현재 버전으로 지정한다. 옛 버전은 그 키로 만든 토큰·자격의 수명이 끝난 뒤 지운다.
  - 유출이 의심되면 수명을 기다리지 않고 바로 지운다. 그 키로 만든 토큰과 자격은 바로 무효가 된다.
  - 연락처 암호화 키와 관리자 TOTP 암호화 키는 지우기 전에 남은 값을 새 버전으로 다시 암호화한다.
- 테스트 프로필의 키는 테스트 전용 값이다. 운영 키와 같게 두지 않는다.
- 비밀값이 저장소에 한 번이라도 올라가면, 이력에서 지우는 것으로 끝내지 않고 제공자에서 새로 발급한다(D-050). 공개 저장소의 이력은 이미 복사됐을 수 있다.

### 6.7 의존성과 저장소

- GitHub의 Dependabot 알림·보안 업데이트, 비밀값 검사, 푸시 차단을 켠다(D-050, 2026-11-08 켬).
- [07 3](07-operations.md#3-운영-목표)의 "배포마다 의존성 검사"는 배포 전에 열린 Dependabot 알림이 없는지 확인하는 것이다. 알림이 있으면 07 3의 기한을 따른다.
- 비밀값 검사 경고가 나오면 그 값을 새로 발급한 뒤 경고를 닫는다.
