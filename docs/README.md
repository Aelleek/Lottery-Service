## 작성 규칙

- 한 사실은 한 문서에만 쓴다. 다른 문서는 그 문서를 링크한다. 예를 들어 보관 기간은 02에만 있고, 04는 "02의 기간"이라고만 쓴다.
- 정책이 바뀌면 해당 문서의 본문을 고치고, 10에 결정을 한 줄 추가한다. 본문 위에 "최신 기준은 다른 문서" 같은 메모를 붙이지 않는다.
- 테이블 컬럼의 정본은 `schema.sql`, 요청·응답 필드의 정본은 `openapi.yaml`이다. 04와 06은 책임과 규칙을 설명한다.
- **[미확인]** 표시는 잠정으로 정한 항목이다. 구현 전에 다시 검토한다. 목록은 10의 2절에 있다.
- ID 체계: 기능은 `F-`·`SF-`·`NX-`·`A-`(01), 결정은 `D-`(확정 결정)·`C-`(잠정 설계 판단)·`Q-`(질문)(10), 수용 시나리오는 `T01`부터(08)다.
- 주기 리뷰 결과는 저장소 루트의 `reviews/`에 남긴다. 이 폴더는 git에서 제외한다.

## 용어

| 용어 | 뜻 |
|---|---|
| 세트, 조합 | 1~45 중 서로 다른 숫자 6개. 순서는 상관없다. `3, 11, 18, 24, 32, 41`이 한 세트다 |
| 추천 1회 | 5세트를 받는 요청 한 번 |
| 회차 | 추첨 단위. 매주 하나다 |
| 판매 마감, 판매 개시 | 회차의 구매 가능 시간의 끝과 시작. 시각은 [02 1](02-policies.md#1-시간과-회차) |
| 주체(subject) | 기록의 주인. 회원 한 명 또는 비회원 브라우저 하나 |
| 비회원 자격 | 서버가 비회원 브라우저에 발급하는 익명 쿠키 |
| 귀속(claim) | 비회원 자격의 기록을 로그인한 회원에게 넘기는 일 |
| 기록(record) | 사용자 화면에 보이는 번호 한 줄. 같은 주체·회차·조합은 한 기록이다 |
| 추천 이력(seen) | 같은 회차에 이미 추천한 조합 목록. 기록을 지워도 남아서 다시 추천하지 않게 한다 |
| 생성 필터 | 기본 추천에서 무작위 후보를 걸러 내는 규칙 7개. 코드 이름은 `LottoValidationRule` |
| 조건 추천 | 사용자가 넣을 번호와 뺄 번호를 고르는 추천. 화면은 후속 기능이다 |
| 게시본(revision) | 우리 서비스가 검증해 공개한 회차 결과의 버전. 공식 결과가 바뀌면 새 게시본이 생긴다 |
| 게시 버전 | 회차의 게시 결과가 바뀔 때마다 1씩 오르는 숫자(`publication_version`). 관리자 승인이 오래된 화면을 보고 실행되는 것을 막는다. 게시본 번호와 다르다 |
| 결과 직접 등록 | 결과 API가 회차 결과를 주지 않을 때 ADMIN이 공식 발표를 보고 결과를 넣는 일(D-034) |
| 판정 | 기록과 게시본을 비교해 등수를 정하는 일 |
| 판정 대기, 금액 미확보, 접수 확인 중 | 화면에서 모두 "확인 중"으로 보일 수 있지만 다른 상태다. 판정 대기는 등수를 아직 모름, 금액 미확보는 등수는 알지만 등수별 금액을 아직 모름, 접수 확인 중은 알림 메시지가 UNKNOWN인 것이다 |
| 마감 봉인(seal) | 판매 마감 시각에 회차를 잠그고 그 마감 시각을 고정하는 일. 알림 대상은 이 시각 전에 생긴 기록과 구매 등록으로 정한다 |
| 기본 알림 | 회차 결과의 안내. 회원·회차당 1건이다. 이미 안내한 내용을 바로잡는 정정 알림은 후속 기능이다(D-042) |
| 발송 슬롯 | 결과 알림을 보내려고 시도하는 정해진 시각. 시각표는 [02 6.2](02-policies.md#62-발송-시각과-재시도) |
| 알림 계획 완료 | 회차의 자동·수동 발송 기한이 끝나고 진행 중인 메시지가 없는 상태. 이 뒤에야 낙첨 기록을 지울 수 있다([05 8.7](05-flows.md#87-알림-계획-완료)) |
| 접수, 전달 | 발송 제공자가 요청을 받은 것, 그리고 실제 사용자에게 도착한 것 |
| UNKNOWN | 제공자가 요청을 받았는지 아직 모르는 상태. 실패가 아니다 |
| 멱등 | 같은 요청을 여러 번 보내도 처리는 한 번만 일어나는 성질 |
| 명령 토큰 | 변경 요청마다 서버가 서명해 발급하는 증명. 누가 어떤 명령을 언제까지 할 수 있는지 담는다 |
| 후속 작업 등록 | 업무 저장과 같은 트랜잭션에 `job` 행을 넣어 "이어서 할 일"을 남기는 방식(C-28). 별도 outbox 테이블은 없다 |
| job, worker | 이어서 할 일 하나, 그리고 그것을 처리하는 프로그램 |
| lease | 시간이 정해진 처리 권한. 시간이 지나면 다른 쪽이 가져갈 수 있다. job 처리권(`job`), 명령 처리권(`command_operation`), 주체당 추천 생성권(`actor_subject`) 세 곳에 쓴다 |
| 운영자 알림 | 서비스 문제를 운영자에게 Discord로 알리는 메시지. 회원 알림과 다르다 |
