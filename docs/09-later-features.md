# 09 후속 기능

첫 출시 다음 단계에서 만들 기능의 정의다. 사용자가 채택했고(D-014, D-018, D-022), 상세 설계는 아직 없다. 각 기능을 설계할 때 이 정의와 [02](02-policies.md)의 공통 정책을 함께 따른다. 이 문서의 수치는 해당 기능에만 쓰는 초기 설정이다.

## 1. 보류: 구매 사이트 자동 입력

- 상태: 사용자 보류(D-009). 재개를 지시하기 전에는 조사·설계·구현을 하지 않는다. 영구 제외는 아니다.
- 목표: 추천 번호 중 살 번호를 고르면 외부 로또 구매 페이지로 이동하고, 그 번호가 입력된 상태까지 연결한다. 사용자가 외부 사이트에서 확인하고 직접 구매한다.
- 단순 클립보드 복사는 대안으로 받아들여지지 않았다. 복사만 만들고 이 기능을 완료로 보지 않는다.
- 외부 사이트가 번호 전달이나 자동 입력을 허용하는지는 확인하지 않았다. 우리 서비스 로그인만으로 다른 사이트 화면을 조작할 권한이 생기지 않는다.
- 2026-10-12 약관 확인: 허용 근거를 찾지 못했다. 이용약관 검색 색인에 접근수단의 제삼자 위임 제한, 제공된 이용방법을 벗어난 이용 금지, 특정 기능의 반복적·규칙적 호출 금지 취지의 조항이 있다. 본인 브라우저에서 한 번 입력을 돕는 방식에 적용되는지는 확정하지 못했다([10 4](10-decisions.md#4-공식-근거)).
- 재개하면 정할 것: 동행복권 고객센터 문의로 적용 여부 확인, 대상 사이트, 회원·비회원 범위, 지원 기기, 자동 입력이 안 될 때의 대체 흐름.

## 2. 사용자 기능

### 2.1 SF-01 여러 장 연속 스캔

- 목적: 복권 여러 장을 연달아 QR로 읽어 한 목록에서 확인한다. 사진 OCR이나 실물 소유 인증이 아니다.
- 흐름: 카메라 허용 → QR 읽기(지원하지 않거나 거부하면 수동 입력) → 회차별로 묶어 목록에 추가 → 항목 수정·제외, 같은 QR 재스캔 경고 → 끝내면 유효·수정 필요·이미 등록 항목 확인 → "결과 확인" 또는 로그인 후 "구매 기록 저장".
- 상태: 읽는 중 → 확인 필요 → 저장·조회 중 → 완료 또는 재확인 필요.
- 규칙: 스캔이나 임시 보관만으로 구매 기록을 만들지 않는다. 같은 조합이라고 같은 실물 복권이라고 단정하지 않는다. 회차별 묶음은 전부 검증 후 한 번에 저장하고, 여러 회차는 회차별 성공·실패를 보여준다.
- 상한: 작업당 20장, 총 100세트. 넘으면 기존 입력을 지우지 않고 나눠 저장하도록 안내한다.
- 수용 기준: 세 장 중 하나가 안 읽혀도 나머지 두 장이 유지된다. 같은 QR을 연달아 비춰도 항목이 늘지 않고 재스캔을 알린다. 저장을 다시 시도해도 기록이 늘지 않는다.

### 2.2 SF-02 조건 추천

- 목적: 넣을 번호와 뺄 번호를 정해 추천받는다. 선택 편의 기능이며 확률을 높인다고 표현하지 않는다.
- 대상: 회원·비회원. 조건을 비우면 기본 추천이다.
- 입력 규칙과 후보 계산은 [02 2.3](02-policies.md#23-조건-추천-입력-범위)에 있다. 생성 필터는 적용하지 않는다(D-028). 합계·홀짝·구간 같은 추가 조건은 포함하지 않는다.
- 흐름: 번호 선택 → 범위·중복·교집합·남은 후보 수 검증 → 조건 요약 확인 → 요청 → 조건을 만족하는 5세트. 적용한 조건과 생성 방식은 결과에 연결해 나중에도 구분한다.
- 실패: 조건을 만족할 수 없으면 이유를 알려 수정하게 한다. 조건을 몰래 완화하거나 일부만 성공으로 저장하지 않는다.
- 예시: 넣을 번호 {7}, 뺄 번호 {13}이면 모든 세트에 7이 있고 13이 없다. 넣을 번호 {7}, 뺄 번호 {7}은 요청 전에 충돌을 표시한다.
- 수용 기준: 모든 결과가 조건과 기본 규칙을 함께 만족한다. 같은 요청 재시도는 같은 결과다. 조건 미충족과 후보 부족을 성공으로 표시하지 않는다.

### 2.3 SF-03 입력 중 임시 보관·복구

- 목적: 수동 입력이나 연속 스캔 도중 화면을 닫거나 통신이 끊겨도 이어서 한다.
- 범위: 아직 제출하지 않은 회차·번호·입력 항목. 같은 기기·브라우저의 로컬 초안이다. 서버 동기화는 하지 않는다(D-016).
- 흐름: 입력하면 보관 상태와 시각 표시(실패하면 "보관됨"으로 표시하지 않음) → 다시 오면 복구 또는 삭제 선택 → 복구한 초안은 회차·번호·권한 재검증 → 사용자가 확인한 뒤 저장. 회차가 지났다고 다음 회차로 바꾸지 않는다.
- 이전 저장 요청의 응답을 못 받았으면, 먼저 그 요청의 처리 결과를 확인한다. 성공이면 완료로 바꾸고, 미확정이면 같은 요청으로 다시 시도한다.
- 보관: 마지막 실제 편집 후 24시간. 단순 조회로 늘지 않는다. 저장에 성공한 항목은 바로 지운다. 회원 로그아웃 시 그 회원의 초안을 지운다. 계정별로 분리하고, 비회원 초안은 확인 후 가져온다. 복권 사진, QR 원문, 토큰은 저장하지 않는다.
- 수용 기준: 화면을 닫았다 열어도 복구 범위를 확인할 수 있다. 저장소를 쓸 수 없으면 입력은 유지하고 보관 실패를 알린다. 응답 유실 뒤 복구해도 기록이 중복되지 않는다. 계정 A의 초안이 계정 B 기록으로 저장되지 않는다.

### 2.4 SF-04 번호 공유 카드

- 목적: 고른 번호와 회차를 카드로 만들어 직접 전달한다. 공동구매, 소유권 양도, 구매 증명이 아니다.
- 흐름: 번호 선택 → 미리보기(회차, 번호, 추천·구매 등록 구분) → 외부 앱 공유, 이미지 저장, 텍스트 복사.
- 규칙: 한 카드 최대 5세트. 당첨금, 실물 QR·바코드, 복권 사진, 회원 이름, 연락처, 내부 ID는 넣지 않는다. 공개 URL이나 공유 게시판은 만들지 않는다. 전달된 이미지를 회수할 수 있다고 안내하지 않는다.
- 수용 기준: 미리보기와 결과의 번호·회차가 같다. 공유를 취소하거나 다시 해도 기록이 바뀌지 않는다. 시스템 공유를 못 쓰면 저장이나 복사를 제공한다.

### 2.5 SF-05 공개 추천 검증 페이지

- 목적: 발표 전에 등록한 추천 실험과 발표 뒤 결과를 누구나 본다. 관리자 실험(3.1)을 공개로 확장한 것이다.
- 목록: 회차, 추천 방식, 상태별 실험. 발표 전에 공개 등록한 실험은 성공·실패·중단을 모두 보여준다.
- 상세: 실험 ID, 대상 회차, 전략·필터 버전, 조건, 입력 자료 기준 시각, 요청·완료 수량, 중복 허용 여부, 등록·완료·확정 시각, 발표 전 확정 번호(페이지 단위), 발표 뒤 등수별 결과, 총 세트와 고유 조합 수, 판정 완료·대기 수, 공식 결과 출처와 게시본. 비율에는 분모를 함께 쓴다.
- 상태: 공개 등록 → 생성 중 → 발표 전 확정 → 결과 대기 → 판정 중 → 판정 완료. 실패, 중단, 발표 전 미확정은 따로 표시한다. 발표 뒤 생성한 것을 발표 전 검증으로 소급하지 않는다.
- 규칙: 주 1회, 전략 1개 10,000세트와 균등 무작위 비교군 10,000세트, 같은 회차·수량·사전 고정 조건. 판매 마감 1시간 전에 확정한다(D-017). 실험은 사용자 중복 제외 규칙 대신 군별 "중복 허용"을 명시하고, 반복 생성과 고유 조합을 따로 공개한다. 난수 seed, 전략, 입력 자료 시각을 기록한다.
- 보관: 공개 실험 원본 3년. 만료 뒤 집계, 등록, 실패, 정정 이력은 비식별로 계속 보존하고 "원본 만료로 완전 재현 불가"를 표시한다.
- 성과가 낮다는 이유로 숨기지 않는다. 개인정보나 보안 노출이 있으면 운영 책임자가 해당 부분만 비공개하고 사유, 시각, 감사 기록을 남긴다. 1등 출현을 보장하지 않는다.
- 수용 기준: 발표 전 확정 목록과 평가 대상이 같다. 실패하거나 1등이 없는 실험도 보인다. 모든 세트가 판정된 뒤에만 "완료 세트 = 1~5등 + 낙첨"을 검사한다. 실험이 회원 사용량, 구매량, 당첨 알림에 섞이지 않는다. 내부 시각이나 해시만으로 외부 기관 인증을 받은 것처럼 표현하지 않는다.

### 2.6 NX-U01 서비스 내 알림함

- 목적: 회원이 당첨 안내, 결과 정정, 문의 답변을 한곳에서 본다. 외부 발송 기록과 별개다.
- 흐름: 사건별 알림 생성 → 종류·회차·시각·읽음 여부와 미확인 개수 → 열면 현재 권한과 원본을 검사한 뒤 관련 화면으로 이동 → 개별·모두 읽음.
- 규칙: 읽음은 화면 확인이지 알림톡 전달 성공이 아니다. 같은 사건의 재처리는 항목을 늘리지 않는다. 원본이 지워졌으면 이용 불가를 안내하고 번호를 다시 보여주지 않는다. 마케팅 알림은 넣지 않는다. 문의 기능이 생기기 전에는 문의 알림을 만들지 않는다.
- 보관: 90일, 개별·전체 삭제, 종류별 배지 끄기(D-019). 알림을 지워도 원본 결과와 정정 이력은 남고, 외부 재발송을 만들지 않는다.

### 2.7 NX-U02 추천 조건 저장·불러오기

- 목적: 회원이 조건 추천의 조건을 이름과 함께 저장한다.
- 흐름: 현재 조건과 이름 확인 → 저장 → 목록 → 불러오기 → 현재 정책으로 재검증 → 사용자가 추천 요청.
- 규칙: 저장과 불러오기는 번호 생성이나 사용량을 만들지 않는다. 정책이 바뀌어도 저장된 조건을 자동으로 바꾸지 않고 "수정 필요"로 표시한다. 동시에 수정하면 충돌을 알린다. 조건을 고쳐도 이미 만든 추천의 당시 조건은 그대로다.
- 상한: 20개, 이름 30자, 같은 이름 허용.

### 2.8 NX-U03 내 기록 검색·태그

- 목적: 회원이 쌓인 기록을 조건으로 찾고 짧은 태그로 분류한다.
- 검색 조건: 회차 범위, 추천·구매 구분, 포함 번호(고른 번호를 모두 포함), 정확한 6개 조합, 당첨 상태, 태그.
- 규칙: 미발표·판정 대기는 낙첨 검색에 넣지 않는다. 조건을 바꾸면 첫 페이지부터 조회한다. 지운 기록은 결과와 태그에서 빠진다. 태그는 번호, 구매 여부, 판정에 영향이 없고 공유 카드에 자동으로 들어가지 않는다.
- 상한: 기록당 태그 10개, 태그 20자, 페이지 10개. 기간은 사용자가 고른다. 느린 조회는 범위를 좁히도록 안내한다. 자유 메모와 첨부는 없다.

### 2.9 NX-U04 로그인 기기 확인·원격 로그아웃

- 목적: 회원이 활성 세션을 보고 공용·분실 기기의 접속을 끊는다.
- 흐름: 계정 화면 → 활성 세션 목록과 현재 세션 표시(브라우저 종류, 최근 사용) → 특정 세션 또는 다른 세션 모두 종료.
- 규칙: 최근 5분 재인증이 필요하다. 이미 종료된 세션의 종료 재시도는 완료로 처리한다. "다른 세션 모두 종료"는 그 시점의 세션에만 적용하고 이후 로그인을 막지 않는다. 위치는 추정이면 추정이라고 쓴다. 소셜 제공자 로그아웃이나 연결 해제를 뜻하지 않는다.
- 보관: 종료·로그인 이력 30일(D-019).

### 2.10 결과 정정 알림

- 목적: 이미 안내한 등수나 금액이 공식 결과 정정으로 틀려졌을 때 회원에게 다시 알린다. 첫 출시는 재판정, 화면 갱신, 운영자 알림까지만 한다([02 6.3](02-policies.md#63-결과가-정정됐을-때), D-042).
- 대상: 안내한 등수가 바뀌었거나 안내한 금액이 틀린 경우다. 낙첨이나 알림 대상 밖 등수로 바뀐 경우도 포함한다. 안내를 받지 않은 대상 기록이 정정으로 알림 대상 등수가 된 경우도 알린다(C-17). 금액이 "확인 중"에서 확정된 것은 정정이 아니다.
- 시간: 요일과 관계없이 09:00~23:30에만 보내고, 밖이면 다음 09:00에 보낸다(D-032). 실패하면 허용 시간 안에서 30분마다 다시 시도하고, 유효기간은 정정 확정 후 7일이다(C-05). 만료된 정정 알림도 정정 확정 후 14일 안에는 수동으로 다시 보낼 수 있다(C-19).
- 규칙: 기본 알림이 아직 접수 확인 중이면 먼저 대조한다. 보내기 직전에 최신 게시본을 다시 확인해 오래된 정정이 최신 내용을 덮어쓰지 않게 한다. A → B → A처럼 실제로 두 번 정정되면 각각 알린다.
- 도입할 때 바꿀 것: 회원·회차당 알림이 1:N(기본 1건과 정정 여러 건)이 되므로 알림 묶음과 메시지를 다시 나눈다. `delivery_message`의 (회원, 회차) 유일 제약을 (회원, 회차, 종류, 순번)으로 바꾼다. 본문을 지운 뒤에도 비교할 수 있게 기록별 마지막 안내 사실을 따로 둔다. 예산의 정정 몫을 다시 떼어 둔다(이전 설계는 20%). 카카오 정정 템플릿 심사를 받는다.
- 참고: 2026-11-02 설계의 원문은 커밋 `691c9c5`의 `docs/02-policies.md` 6.3, `docs/05-flows.md` 8.5, `docs/contracts/schema.sql`(`notification_cycle`, `notification_intent`, `notification_communicated_fact`)에 있다.

## 3. 관리자·운영 기능

### 3.1 A-01 추천 번호 검증

사용자가 2026-10-08에 추가한 요구다. 관리자가 "추천 기능이 규칙대로 동작하는가"와 "생성한 번호가 실제로 어떤 결과를 냈는가"를 확인한다.

| 방법 | 확인하는 것 |
|---|---|
| 생성 규칙 확인 | 모든 세트가 기본 규칙과 생성 필터를 지키는가. 요청한 수량이 만들어지는가 |
| 과거 회차 비교 | 고른 과거 회차의 결과와 비교하면 등수별로 어떤가 |
| 발표 전 생성 후 비교 | 발표 전에 저장한 번호가 발표 뒤 어떤 결과를 냈는가 |

- 기능의 정확성(번호 범위, 중복, 수량, 판정, 재현성)과 관측 성과를 나눈다. 1등이 나왔다는 사실을 예측력의 증거로 쓰지 않고, 1등이 안 나왔다고 오류로 보지 않는다.
- 과거 회차를 평가할 때는 그 회차 발표 전에 알 수 있던 자료만 쓴다. 생성 필터의 과거 1등 비교도 그 회차 이전 결과만 쓴다([03 2](03-architecture.md#2-패키지)).
- 실험마다 대상 회차, 전략과 필터 버전, 생성 시각, 요청·완료 수량을 남긴다. 총 세트, 고유 조합, 등수별 세트와 비율, 낙첨 수를 보여준다. 같은 회차·수량의 균등 무작위 결과를 비교군으로 함께 본다.
- 발표 전에 저장한 번호는 바꾸지 않는다. 바꿔서 다시 하면 새 실험이다.
- 실험 번호는 회원 기록, 사용량, 당첨 알림에 섞지 않는다. 중단 후 다시 실행해도 중복 집계하지 않는다.
- 상한: 작업당 20,000세트, 동시 1개, 묶음 1,000세트, 하루 40,000세트, 실험 저장 공간 2GiB에서 경보와 새 실행 차단. 사용자 응답 목표를 5분 넘게 못 지키면 실험부터 멈춘다(D-010, D-020). 내부 비공개 실험 원본은 90일 보관한다.
- 요구사항 예시의 100만 세트는 이 상한의 50배다. 부하와 저장 비용을 확인한 뒤 확대를 정한다(10 3절 Q-02).

### 3.2 A-03 공개 검증 운영

- 권한 있는 관리자가 실험 시작 전에 공개 대상으로 등록하고 회차, 방식, 수량, 조건, 확정 마감을 기록한다.
- 확정 뒤에는 조건과 번호를 바꾸지 않는다. 다시 하면 새 실험 ID와 이전 실험 참조를 남긴다.
- 진행률과 실패 이유를 보고, 저장된 번호를 바꾸지 않는 범위에서 재개한다. 미완료 수량을 요청 수량으로 부풀리지 않는다.
- 발표 뒤 성과를 보고 공개 여부를 고른 실험은 사전 공개 검증으로 분류하지 않는다.
- 공식 결과가 정정되면 새 게시본으로 다시 평가한다. 설명 문구를 고쳐도 변경자, 시각, 사유를 남긴다.
- 관리자 화면과 공개 화면은 같은 실험 자료를 읽어 숫자가 어긋나지 않게 한다.

### 3.3 NX-O01 주요 이용 흐름 자동 점검

- 운영 환경에서는 공개 결과와 공개 검증 페이지를 읽기로 점검하고, 회원 저장·연속 스캔·초안 복구는 별도 테스트 환경에서 점검한다. 실제 결제, 광고, 사용자 문자 발송은 점검하지 않는다.
- 점검 명세(대상, 기대 결과, 시간대, 제한 시간, 주기)를 등록하고, 점검 대상 URL은 허용 목록으로 제한한다.
- HTTP 200이어도 로그인 HTML이나 잘못된 회차면 실패로 본다. 예정된 미발표는 오류가 아니다. 점검 도구가 멈추면 마지막 정상 결과를 계속 정상으로 표시하지 않는다.
- 초기값: 5분 간격, 3회 연속 실패 시 운영자 알림.

### 3.4 NX-O02 연동·키·인증서 만료 관리

- 자원별로 담당자, 영향 기능, 환경, 만료일 또는 다음 확인일, 비밀 저장소 참조를 등록한다. 비밀 원문은 화면, 로그, 내보내기에 넣지 않는다.
- 갱신은 승인된 경로로 하고, 실제 연동이 정상인지 확인한 뒤 이전 자격을 폐기한다. 날짜만 고쳐 정상 처리하지 않는다.
- 만료 30, 14, 7, 1일 전 운영자 알림은 첫 출시부터 한다([07 2.1](07-operations.md#21-언제-보내는가)). 이 기능은 그 목록을 관리하는 화면과 절차다.

### 3.5 NX-O03 공개 장애·점검 현황

- 회원·비회원이 로그인 없이 장애 범위와 대안을 본다. 기능별 정상, 지연, 중단, 복구 확인 중, 확인 불가를 표시한다.
- 주 애플리케이션과 따로 배포할 수 있는 정적 안내 경로를 쓴다. 이 경로를 확보하기 전에는 앱 전체 장애 때도 안내할 수 있다고 하지 않는다.
- 회원 정보, 내부 주소, 원문 오류는 공개하지 않는다. 경보만 보고 해결 처리하지 않는다.
- 공지 시간 목표는 [07 3](07-operations.md#3-운영-목표)을 따른다.

### 3.6 NX-O04 의존성·보안 업데이트 관리

- 배포 산출물별 런타임, 직접·간접 의존성, 이미지 목록을 확보하고 점검 → 영향 검토 → 업데이트·완화 → 회귀 검증 → 배포 버전 확인 순서로 처리한다.
- 경고를 숨기거나 버전 문자열만 바꿔 해결하지 않는다. 자동 업데이트를 검증 없이 병합·배포하지 않는다.
- 기존 저장소, CI, 이슈 관리로 시작한다. 전용 화면은 필수가 아니다. 처리 기준은 [07 3](07-operations.md#3-운영-목표)에 있다.

### 3.7 NX-O05 대량 실험 자원 관리

- 실행 전에 요청 수량, 예상 저장량, 현재 부하를 확인하고, 상한 안에서 자원을 예약하거나 대기·거절한다.
- 여러 관리자 요청의 합계에도 같은 상한을 적용한다. worker가 죽은 뒤 예약을 회수할 때는 실제 실행 소유권과 대조한다.
- 과부하가 오면 실험을 먼저 제한하고, 완료된 번호와 진행 위치를 보존한다. 공간이 부족하다고 사용자 기록이나 공개 검증 증거를 지우지 않는다.

### 3.8 문의 지원

- 운영 기반 6묶음 중 하나로, 후속이다.
- 회원 문의 접수, 처리 상태, 공개 답변과 내부 메모를 나눈다. 공개 답변만 알림함에 반영한다. 관련 요청은 가린 증거로 연결한다.
