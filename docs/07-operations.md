# 07 운영

## 1. 작업 일정

시각은 서울 기준이다. "추첨일"은 회차 일정의 추첨 날짜이고, 기본은 토요일이다.

| 작업 | 언제 | 하는 일 |
|---|---|---|
| 회차 개시 | 판매 개시 시각(기본 일 06:00) | 추천과 기본 내역을 새 회차로 바꾼다 |
| 마감 봉인 | 판매 마감 시각(기본 토 20:00) | 회차를 봉인한다 |
| 대상 고정 | 봉인 직후 | 마감 시점 상태로 알림 주기와 대상을 만든다 |
| 결과 수집 | 추첨 10분 뒤부터 5분 간격, 게시될 때까지. 다음 날 12:00 이후로는 1시간 간격 **[미확인]** | 결과 API를 읽고 검증해 게시한다 |
| 결과 알림 슬롯 | [02 6.2](02-policies.md#62-발송-시각과-재시도)의 시각 | 기본 알림을 보내거나 다시 시도한다 |
| 정정 알림 | 정정이 확인되면 [02 6.3](02-policies.md#63-정정-알림)의 허용 시간 안에서 | 정정 알림을 보낸다 |
| 판정 | 결과 게시, 기록 생성·가져오기 사건이 생길 때 | 등수를 판정한다 |
| 미평가 대조 | 매시간 | 최근 35일 회차에서 판정이 빠진 기록을 찾는다 |
| 접수 대조 | 10분 간격 | UNKNOWN 메시지를 콜백·제공자 조회로 대조한다 |
| 집계 | 사건이 생길 때. 일·월·회차 봉인은 기간이 끝난 뒤 | 사용량을 집계하고 범위를 봉인한다 |
| 보관 정리 | 매일 04:00 | 보관 기간이 지난 기록과 비회원 주체를 정리한다 |
| 탈퇴 삭제 | 탈퇴 직후 | 개인 자료를 지운다. 목표 시간은 [02 7.3](02-policies.md#73-탈퇴와-재가입) |
| 예산 월 전환 | 매월 1일 00:00 | 새 달 예산 행을 만든다 |
| 백업 | 매일, 그리고 변경 로그 상시 | 4절 |

"10분 뒤", "매시간", "04:00" 같은 작업 주기는 초기 설정이다 **[미확인]**.

결과 수집이 실패했다는 이유만으로 운영자 알림을 보내지는 않는다. 결과가 늦어지면 결과 알림 슬롯이 실패하고, 그 슬롯의 운영자 알림이 원인을 알려 준다.

## 2. 운영자 알림

운영자 알림은 Discord 웹훅으로 보낸다(D-030). 웹훅 주소는 `config/integrations.yml`에 둔다.

### 2.1 언제 보내는가

| 사건 | 시점 | 내용 |
|---|---|---|
| 결과 알림 슬롯 실패 | 운영자 알림 대상 슬롯([02 6.2](02-policies.md#62-발송-시각과-재시도))이 실패했을 때(D-027) | 회차, 슬롯, 원인, 대상 수, 미발송 수, UNKNOWN 수. 마지막 슬롯이면 "자동 발송 종료"와 수동 다시 보내기 안내 |
| 정정 알림 실패 | 첫 실패, 그리고 유효기간 만료 **[미확인]** | 회차, 원인, 미발송 수 |
| 수동 다시 보내기 결과 | 실행이 끝났을 때 | 회차, 실행한 운영자, 성공·실패 수 |
| 공식 결과 격리 | 게시한 결과와 다른 결과가 왔을 때 | 회차, 바뀐 항목. 승인 필요 안내 |
| 메시지 예산 | 월 예산 80% 도달, 그리고 예산 때문에 발송이 막혔을 때 | 사용액, 남은 액, 막힌 건수 |
| 운영비 | 월 운영비 80% 도달 | 사용액 |
| 접수 확인 장기화 | UNKNOWN이 24시간 넘게 풀리지 않을 때 **[미확인]** | 건수, 가장 오래된 시각 |
| 작업 실패 | job이 DEAD가 됐을 때 | 작업 종류, 마지막 오류 코드 |
| 삭제 기록 저장 실패 | 탈퇴 journal 저장이 실패했을 때 | 삭제 요청 외부 ID |
| 정리 지연 | 보관 기간이 지났는데 보호 조건 때문에 7일 넘게 못 지운 데이터 **[미확인]** | 범위, 건수, 이유 |
| 인증서·연동 만료 | 만료 30, 14, 7, 1일 전 | 대상, 만료일 |

### 2.2 원인 코드

| 코드 | 뜻 |
|---|---|
| `RESULT_NOT_PUBLISHED` | 결과 API가 아직 그 회차를 주지 않는다 |
| `RESULT_FETCH_ERROR` | 결과 API 호출이나 응답 검증이 실패했다 |
| `RESULT_QUARANTINED` | 결과가 격리돼 운영자 승인을 기다린다 |
| `EVALUATION_PENDING` | 결과는 있지만 판정이 끝나지 않았다 |
| `PROVIDER_ERROR` | 발송 제공자가 요청을 받지 않았다 |
| `BUDGET_EXHAUSTED` | 월 예산 때문에 보내지 못했다 |
| `PARTIAL_FAILURE` | 일부 회원만 실패했다. 건수를 함께 보낸다 |

### 2.3 규칙

- 내용에 전화번호, 번호 조합, 회원 ID, 토큰을 넣지 않는다. 회차, 건수, 원인 코드, 관리자 화면 경로만 넣는다 **[미확인]**.
- 같은 사건은 한 번만 보낸다. 운영자 알림도 job이고, 중복 키는 (사건 종류, 대상, 슬롯)이다.
- Discord 전송이 실패하면 job으로 다시 보낸다. Discord가 멈춰도 회원 기능에는 영향이 없다. 보내지 못한 운영자 알림은 관리자 화면에서 확인한다.

## 3. 운영 목표

모두 초기 설정이고 측정값이 아니다(D-020). 실제 배포에서 측정한 뒤 조정한다.

| 항목 | 목표 |
|---|---|
| 처리량 | 초당 20요청, 동시 사용자 100명의 부하 시험에서 조회 p95 1초, 추천 저장 p95 2초, 서버 오류율 1% 미만 |
| 가용성 | 월 99.5%. 내부 목표이며 보장하지 않는다 |
| 운영비 | 월 100,000원(VAT 포함, [메시지 예산](02-policies.md#65-비용) 포함). 80%에서 운영자 알림. 자동 증설·충전 없음 |
| 복구 | 데이터 손실 최대 1시간(RPO), 복구 시간 4시간(RTO) |
| 장애 공지 | 담당자가 확인한 때부터 30분 안에 첫 공지, 진행 중에는 60분마다 갱신. 원인을 모르면 추측을 확정처럼 쓰지 않는다 |
| 보안 업데이트 | 배포마다 의존성 검사, 주간 점검. 실제로 닿을 수 있는 중대 취약점은 새 배포를 막고 24시간 안에 영향 판단, 72시간 안에 완화. 예외는 책임자, 이유, 최대 7일 재검토 기한을 남긴다 |

운영 도구는 기존 CI, 접근이 제한된 관리 명령, DB 작업 큐로 시작한다. 전용 유료 상태·비밀 관리 서비스는 처음에 도입하지 않는다.

무인 24시간 대응은 약속하지 않는다. 운영 책임자 역할 하나를 두고, 배포 담당자가 장애·복구·키 갱신을 겸한다. 실제 담당 계정, 비밀 저장소, 연락 경로는 배포 전에 등록한다.

## 4. 백업과 복원

- 일별 백업을 [02 8](02-policies.md#8-보관과-삭제)의 기간만큼 보관한다. 일별 백업만으로는 1시간 RPO를 맞출 수 없으므로 변경 로그(binlog) 같은 수단을 함께 둔다. 변경 로그와 복제본도 같은 기간 안에서만 복원할 수 있게 한다.
- 격리 환경에서 월 1회, 그리고 파괴적인 데이터 변경 전에 복원 연습을 한다.
- 복원 절차:
  1. 외부 발송, 로그인, 쓰기를 멈춘다.
  2. 백업과 변경 로그로 복원한다.
  3. 최신 삭제 기록(journal)을 다시 적용한다. 확보하지 못하면 여기서 멈추고 서비스를 열지 않는다.
  4. 모든 세션을 회수한다.
  5. 발송 상태를 제공자와 대조한다.
  6. 단계적으로 서비스를 연다.

## 5. 출시 조건

정책을 정한 것과 출시할 수 있는 것은 다르다. 아래를 실제로 확인해야 출시한다.

1. **결과 원천.** 실제 판매 일정 예외, 과거·최신·미발표 결과의 실제 응답, 등수별 금액 표본. 결과 조회 빈도(1절)가 동행복권 이용약관의 반복 호출 제한에 해당하지 않는지 확인([10 4](10-decisions.md#4-공식-근거)).
2. **소셜 로그인.** 제공자별 앱 설정, 콜백, 재인증.
3. **알림톡.** 비즈니스 채널, 템플릿 3종(기본, 정정, 인증) 심사 승인, 번호 인증, 콜백 진위 검증 또는 인증된 상태 조회, 중복 접수 안전성, SMS 대체 발송 꺼짐.
4. **운영 환경.** 호스팅·백업 견적, 운영 계정과 담당자, 관리자 다중 요소 인증, Discord 웹훅, 부하 시험, 복원 시험과 삭제 기록 재적용.
