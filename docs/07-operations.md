# 07 운영

## 1. 작업 일정

시각은 서울 기준이다. "추첨일"은 회차 일정의 추첨 날짜이고, 기본은 토요일이다.

| 작업 | 언제 | 하는 일 |
|---|---|---|
| 회차 개시 | 판매 개시 시각(기본 일 06:00) | 추천과 기본 내역을 새 회차로 바꾼다 |
| 마감 봉인 | 판매 마감 시각(기본 토 20:00) | 회차를 봉인하고 마감 시각을 고정한다. 알림 대상은 슬롯에서 이 시각으로 정한다([05 5](05-flows.md#5-회차-마감과-알림-대상)) |
| 결과 수집 | 추첨 10분 뒤부터 5분 간격, 게시될 때까지. 다음 날 12:00 이후로는 1시간 간격 **[미확인]** | 결과 API를 읽고 검증해 게시한다 |
| 결과 알림 슬롯 | [02 6.2](02-policies.md#62-발송-시각과-재시도)의 시각 | 기본 알림을 보내거나 다시 시도한다 |
| 판정 | 결과 게시, 기록 생성·가져오기 사건이 생길 때 | 등수를 판정한다 |
| 미평가 대조 | 매시간 | 최근 35일 회차에서 판정이 빠진 기록을 찾는다 |
| 접수 대조 | 10분 간격 | UNKNOWN 메시지를 제공자 메시지 조회로 대조한다(C-27) |
| job 회수 | 1분 간격 | lease가 만료된 RUNNING job을 RETRY_WAIT로 돌린다. 시도 5회를 넘기면 DEAD **[미확인]** |
| 집계 | 매시간 최근 기간을 다시 계산. 일·월·회차 확정은 보정 기간이 끝난 뒤 | 원천에서 다시 계산해 덮어쓰고, 보정 기간 뒤 VERIFIED로 확정한다 |
| 보관 정리 | 매일 04:00 | 보관 기간이 지난 기록, 비회원 주체, 비동기·발송 기록을 정리한다. 알림 계획 완료 조건([05 8.7](05-flows.md#87-알림-계획-완료))과, 달마다 예산 카운터와 메시지 비용 합계([05 8.4](05-flows.md#84-예산))도 이때 확인한다 |
| 탈퇴 삭제 | 탈퇴 직후 | 개인 자료를 지운다. 목표 시간은 [02 7.3](02-policies.md#73-탈퇴와-재가입) |
| 예산 월 전환 | 매월 1일 00:00 | 새 달 예산 행을 만든다 |
| 백업 | 매일, 그리고 변경 로그 상시 | 4절 |

"10분 뒤", "매시간", "04:00" 같은 작업 주기는 초기 설정이다 **[미확인]**.

결과 수집이 실패했다는 이유만으로 운영자 알림을 보내지는 않는다. 결과가 늦어지면 결과 알림 슬롯이 실패하고, 그 슬롯의 운영자 알림이 원인을 알려 준다.

## 2. 운영자 알림

운영자 알림은 Discord 웹훅으로 보낸다(D-030). 웹훅 주소는 `config/integrations.yml`에 둔다.

### 2.1 언제 보내는가

| 사건 | 시점 | 내용 |
|---|---|---|
| 결과 알림 슬롯 실패 | 운영자 알림 대상 슬롯([02 6.2](02-policies.md#62-발송-시각과-재시도))이 실패했을 때(D-027) | 회차, 슬롯, 원인, 대상 수, 미발송 수(그중 예산 차단 수와 제공자 미접수·거절 수를 따로), UNKNOWN 수. 원인 코드는 하나만 남긴다(예산 차단이 하나라도 있으면 BUDGET_EXHAUSTED). 마지막 슬롯이면 "자동 발송 종료"와 수동 다시 보내기 안내 |
| 공식 결과 정정 반영 | 정정 게시본의 판정이 끝났을 때 | 회차, 등수나 금액이 바뀐 회원 수, 새로 대상이 된 회원 수. 정정 알림은 보내지 않는다는 안내(D-042) |
| 수동 다시 보내기 결과 | 실행이 끝났을 때 | 회차, 실행한 운영자, 성공·실패 수 |
| 공식 결과 격리 | 게시한 결과와 다른 결과가 왔을 때 | 회차, 바뀐 항목. 승인 필요 안내 |
| 결과 직접 등록 | ADMIN이 결과를 직접 등록했을 때(D-034) | 회차, 등록한 관리자 역할. 번호는 넣지 않는다 |
| 메시지 예산 | 월 예산 80% 도달, 그리고 예산 때문에 발송이 막혔을 때 | 사용액, 남은 액, 막힌 건수 |
| 예산 카운터 불일치 | 달마다 대조에서 카운터와 메시지 비용 합계가 다를 때 | 달, 카운터 값, 메시지 합계 |
| 운영비 | 월 운영비 80% 도달 | 사용액. 앱이 보내지 않고 호스팅 제공자의 청구(예산) 알림으로 받는다(2.3) |
| 접수 확인 장기화 | UNKNOWN이 24시간 넘게 풀리지 않을 때 **[미확인]** | 건수, 가장 오래된 시각 |
| 접수 확인 종결 | UNKNOWN을 대조 기간([02 6.2](02-policies.md#62-발송-시각과-재시도)) 안에 확정하지 못해 FAILED로 끝냈을 때 | 회차, 건수 |
| 작업 실패 | job이 DEAD가 됐을 때 | 작업 종류, 마지막 오류 코드 |
| 삭제 기록 저장 실패 | 탈퇴 journal 저장이 실패했을 때 | 삭제 요청 외부 ID |
| 정리 지연 | 보관 기간이 지났는데 보호 조건 때문에 7일 넘게 못 지운 데이터 **[미확인]** | 범위, 건수, 이유 |
| 인증서·연동 만료 | 만료 30, 14, 7, 1일 전 | 대상, 만료일 |
| 보안 신호 | 10분 동안 429, CSRF 거절, 출처 검사 거절 가운데 하나가 1,000건을 넘을 때 **[미확인]** | 종류, 건수, 많이 걸린 경로. IP 원문은 넣지 않는다 |
| 관리자 인증 | 관리자 2차 인증 잠금, 관리자 권한 부여·회수, 2차 인증 초기화([03 6.3](03-architecture.md#63-인증과-관리자)) | 사건 종류, 역할 |

### 2.2 원인 코드

| 코드 | 뜻 |
|---|---|
| `RESULT_NOT_PUBLISHED` | 결과 API가 아직 그 회차를 주지 않는다 |
| `RESULT_FETCH_ERROR` | 결과 API 호출이나 응답 검증이 실패했다 |
| `RESULT_QUARANTINED` | 결과가 격리돼 운영자 승인을 기다린다 |
| `EVALUATION_PENDING` | 결과는 있지만 판정이 끝나지 않았다 |
| `PROVIDER_ERROR` | 발송 제공자가 요청을 받지 않았다 |
| `BUDGET_EXHAUSTED` | 월 예산 때문에 보내지 못했다 |
| `PARTIAL_FAILURE` | 일부 회원만 실패했다. 건수를 함께 보낸다 |

### 2.3 규칙

- 내용에 전화번호, 번호 조합, 회원 ID, 토큰, IP 원문을 넣지 않는다. 회차, 건수, 원인 코드, 관리자 화면 경로만 넣는다 **[미확인]**.
- 같은 사건은 한 번만 보낸다. 운영자 알림도 job이고, 중복 키는 (사건 종류, 대상, 슬롯)이다. 슬롯이 없는 사건은 그 사건을 구분하는 값을 쓴다. 예를 들어 결과 격리는 (격리, 회차, 결과의 `semantic_hash`)다.
- 운영비 80% 알림은 앱이 보내지 않는다. 호스팅 제공자의 청구(예산) 알림을 월 운영비의 80%로 설정하고, 받는 곳을 운영자 메일로 둔다. 호스팅을 정할 때 설정하고 출시 조건(5절 4번)에서 확인한다.
- Discord 전송이 실패하면 job으로 다시 보낸다. Discord가 멈춰도 회원 기능에는 영향이 없다. 보내지 못한 운영자 알림은 관리자 화면에서 확인한다.

## 3. 운영 목표

모두 초기 설정이고 측정값이 아니다(D-020). 실제 배포에서 측정한 뒤 조정한다.

| 항목 | 목표 |
|---|---|
| 처리량 | 초당 20요청, 동시 사용자 100명의 부하 시험에서 조회 p95 1초, 추천 저장 p95 2초, 서버 오류율 1% 미만 |
| 가용성 | 월 99.5%. 내부 목표이며 보장하지 않는다 |
| 운영비 | 월 100,000원(VAT 포함, [메시지 예산](02-policies.md#65-비용) 포함). 80%에서 운영자 알림. 자동 증설·충전 없음 |
| 복구 | 데이터 손실 최대 1시간(RPO), 복구 시간 4시간(RTO) |
| 장애 공지 | 담당자가 확인한 때부터 30분 안에 첫 공지, 진행 중에는 60분마다 갱신. 원인을 모르면 추측을 확정처럼 쓰지 않는다 |
| 보안 업데이트 | 배포마다 의존성 검사, 주간 점검. 실제로 닿을 수 있는 중대 취약점은 새 배포를 막고 24시간 안에 영향 판단, 72시간 안에 완화. 예외는 책임자, 이유, 최대 7일 재검토 기한을 남긴다 |

운영 도구는 기존 CI, 접근이 제한된 관리 명령, DB 작업 큐로 시작한다. 전용 유료 상태·비밀 관리 서비스는 처음에 도입하지 않는다.

무인 24시간 대응은 약속하지 않는다. 운영 책임자 역할 하나를 두고, 배포 담당자가 장애·복구·키 갱신을 겸한다. 실제 담당 계정, 비밀 저장소, 연락 경로는 배포 전에 등록한다.

## 4. 백업과 복원

- 일별 백업을 [02 8](02-policies.md#8-보관과-삭제)의 기간만큼 보관한다. 일별 백업만으로는 1시간 RPO를 맞출 수 없으므로 변경 로그(binlog) 같은 수단을 함께 둔다. 변경 로그와 복제본도 같은 기간 안에서만 복원할 수 있게 한다.
- 격리 환경에서 월 1회, 그리고 파괴적인 데이터 변경 전에 복원 연습을 한다.
- 백업과 변경 로그는 암호화해 저장하고, 운영 책임자만 읽을 수 있게 한다. 백업이 새면 DB가 새는 것과 같다. 방법은 호스팅과 함께 정한다(5절).
- 복원 절차:
  1. 외부 발송, 로그인, 쓰기를 멈춘다.
  2. 백업과 변경 로그로 복원한다.
  3. 최신 삭제 기록(journal)을 다시 적용한다. 확보하지 못하면 여기서 멈추고 서비스를 열지 않는다.
  4. 모든 세션을 회수한다.
  5. 발송 상태를 제공자와 대조한다.
  6. 단계적으로 서비스를 연다.

## 5. 출시 조건

정책을 정한 것과 출시할 수 있는 것은 다르다. 아래를 실제로 확인해야 출시한다.

1. **결과 원천.** 실제 판매 일정 예외, 과거·최신·미발표 결과의 실제 응답(2026-11-10 표본 확보: 1249회, 1회, 추첨 전 1250회 빈 목록), 등수별 금액 표본. 결과 조회 빈도(1절)가 동행복권 이용약관의 반복 호출 제한에 해당하지 않는지 약관 전체를 다시 확인([10 4](10-decisions.md#4-공식-근거), D-060). robots.txt는 2026-11-10에 `/resources/`, `/winImages/`만 막았다.
2. **소셜 로그인.** 제공자별 앱 설정, 콜백, 재인증.
3. **알림톡.** 비즈니스 채널, 템플릿 2종(기본, 인증) 심사 승인, 번호 인증, 메시지 조회 API로 알림톡 상태 확인(요청 키를 넣은 `customFields`로 메시지를 찾을 수 있는지 포함), 중복 접수 안전성, SMS 대체 발송 꺼짐.
4. **운영 환경.** 호스팅·백업 견적, 운영 계정과 담당자, 관리자 다중 요소 인증(D-047)의 등록과 복구, Discord 웹훅, 부하 시험, 복원 시험과 삭제 기록 재적용. 삭제 기록(journal) 저장소의 종류, 보관, 가용성 확인. 저장소는 운영 DB 밖에 두고, 추가만 하고, 37일 보관하고, 저장 확인을 받은 뒤 지운다. 종류는 호스팅과 함께 정한다(D-052). 이 저장소가 멈추면 탈퇴 처리가 멈춘다([04 6.2](04-data.md#62-탈퇴할-때)).
5. **서버와 네트워크 보안.** 호스팅을 고를 때 함께 정한다.
   - DB는 외부에 열지 않는다. 앱 서버에서만 닿는다.
   - 서버 관리 접속은 키 방식으로 하고 접속할 수 있는 곳을 제한한다. 외부에는 HTTPS 포트만 연다.
   - OS와 런타임 보안 업데이트를 누가 언제 적용하는지 정한다.
   - 운영 비밀값을 둘 곳과 읽을 수 있는 계정([03 6.6](03-architecture.md#66-비밀값과-키)).
   - 백업의 암호화와 접근 권한(4절).
   - 대규모 공격(DDoS)을 막는 앞단 방식. CDN·방화벽 서비스를 쓸지, 호스팅 기본 보호에 맡길지 정한다(D-049). 앞단 서비스를 쓰면 서버 IP를 숨기고, 서버 방화벽은 그 앞단에서 오는 연결만 받는다.
   - HTTPS 인증서 자동 갱신.
   - 앞단 뒤에 두면 앞단이 붙인 클라이언트 IP 헤더만 믿도록 서버를 설정하고(환경 변수 `LOTTERY_TRUSTED_PROXIES`에 앞단의 연결 주소 정규식, `server.tomcat.remoteip.internal-proxies`), 요청 제한이 사용자별로 세어지는지 확인한다. 설정을 빠뜨리면 모든 요청이 앞단 IP 하나로 세어져 정상 사용자가 429를 받는다.
   - http → https 이동은 앞단에서 한다. 앱은 앞단이 붙인 프로토콜 헤더만 믿는다(위와 같은 설정). 운영 주소의 응답에 HSTS가 있는지 확인한다.
6. **보안 점검.** 운영 설정에서 [03 6](03-architecture.md#6-보안)의 항목과 [08 5](08-delivery.md#5-수용-시나리오)의 보안 시나리오(T58~T65)를 확인한다. 응답 헤더, 쿠키 속성, 열지 않는 경로, 요청 제한, 열린 Dependabot 알림 0건, 열린 비밀값 검사 경고 0건이다. 2026-11-08에 찾은 OAuth 클라이언트 시크릿 노출(7절 예시)은 이 전에 새로 발급해야 한다.
7. **개인정보 법적 확인.** 개인정보 처리방침과 수집·이용 동의 문구. 앞단 서비스나 해외 업체(호스팅, 발송, 백업)를 쓰면 처리 위탁과 국외 이전 안내가 필요한지. 개인정보가 유출됐을 때 회원 통지와 신고의 기한·대상(7절) **[미확인]**.

## 6. 데이터 이행

현재 DB 자료는 새 구조로 옮기지 않는다. 이유와 처리는 [08 4](08-delivery.md#4-데이터-이행)에 있다.

## 7. 보안 사고 대응

키 유출, 관리자 계정 도용, 개인정보 유출, 비정상적인 대량 접근이 의심되면 아래 순서로 한다(C-32). 무인 24시간 대응은 약속하지 않지만(3절), 확인한 때부터는 이 순서를 따른다.

1. **기록을 시작한다.** 언제 무엇을 봤는지 적는다. 로그와 감사 기록은 지우거나 덮어쓰지 않고 보존한다. 보관 정리가 증거를 지우지 않도록, 필요하면 해당 회차의 정리를 보류한다(`lotto_round.cleanup_held`).
2. **막는다.** 상황에 맞는 것을 고른다.
   - 유출된 키: 제공자에서 새로 발급하고, 앱 키는 옛 버전을 바로 지운다([03 6.6](03-architecture.md#66-비밀값과-키)).
   - 관리자 계정: 권한을 회수하고 2차 인증을 초기화한다.
   - 회원 세션: 모든 서버 세션을 지우고 모든 회원의 `auth_version`을 올린다. 비회원 자격은 자격 해시 키의 옛 버전을 지워 무효로 한다. 회원과 비회원 모두 다시 로그인하거나 새 자격을 받는다.
   - 외부 발송을 멈추거나, 필요하면 쓰기를 막고 읽기만 연다.
3. **범위를 확인한다.** 감사 기록, 서버 로그, 제공자 기록으로 어떤 자료가 누구에게 얼마나 노출됐는지 본다.
4. **알린다.** 개인정보가 유출됐으면 법령이 정한 기한 안에 회원에게 알리고, 정해진 기관에 신고한다. 기한과 대상은 출시 전에 확인한다(5절 7번) **[미확인]**. 서비스에 영향이 있으면 장애 공지 규칙(3절)도 따른다.
5. **고치고 남긴다.** 원인을 고치고, 같은 일이 다시 생기지 않게 하는 조치를 결정 기록에 남긴다.

예시: 2026-11-08 GitHub 비밀값 검사가 공개 저장소 이력에서 OAuth 클라이언트 시크릿을 찾았다. 2025-06-03 커밋에서 Google·카카오·네이버 시크릿이 함께 올라갔고, 파일을 git에서 뺀 뒤에도 같은 값을 계속 쓰고 있었다. 막는 일은 세 제공자에서 시크릿을 새로 발급하는 것이다. 아직 출시 전이라 알릴 회원은 없다. 재발 방지로 비밀값 검사와 푸시 차단을 켰다(D-050).
