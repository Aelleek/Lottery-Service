# 05 처리 흐름

데이터가 추천에서 탈퇴까지 어떤 단계로 움직이는지 설명한다. 규칙의 수치는 [02](02-policies.md), 테이블은 [04](04-data.md), 요청 형식은 [06](06-api.md)에 있다.

## 1. 비회원 자격 발급

1. 쿠키가 없는 브라우저가 처음 들어오면 화면이 `POST /guest-credentials`를 부른다.
2. 서버는 Origin과 Fetch Metadata를 검사하고, IP별 발급 속도 제한을 확인한다.
3. 비회원 주체와 자격을 만들고, 자격 원문은 쿠키로만 내려준다. DB에는 해시만 저장한다.
4. 유효한 자격이 이미 있으면 새로 만들지 않고 같은 주체를 유지한다. 회원 세션이 있으면 발급하지 않는다.

## 2. 추천

1. 화면이 명령 토큰을 받는다. 토큰에는 주체, 명령 종류, 회차, 일정 버전, 만료 시각이 묶여 있다([06 1](06-api.md#1-공통-규칙)).
2. 추천 요청이 들어오면 트랜잭션 밖에서 입력을 검증한다. 조건 추천이면 후보 수를 계산하고 5보다 작으면 바로 실패한다.
3. 주체의 생성 lease를 잡는다. 이미 생성 중이거나 최소 간격([02 2.1](02-policies.md#21-기본-규칙))이 안 지났으면 다시 시도할 시각을 알려 준다.
4. 같은 회차의 추천 이력을 읽는다. 귀속한 비회원 이력도 합친다.
5. 후보를 만든다.
   - 기본 추천: 무작위 6개 → 생성 필터 7개 → 이력 중복 검사. 걸리면 다시 뽑는다.
   - 조건 추천: 넣을 번호를 고정하고 남은 숫자에서 무작위로 채운 뒤 이력 중복만 검사한다.
   - 1,000번 시도하거나 250ms가 넘으면 멈춘다. 조건 추천의 후보가 10만 개 이하라면 전부 나열해 남은 조합에서 5개를 고른다. 전부 나열해서 5개 미만이면 후보 부족, 시간 안에 끝내지 못했으면 계산 지연이다. 둘을 구분해 알린다.
6. 짧은 트랜잭션을 연다. 주체 → 회차 순서로 잠근다.
7. 잠금을 잡은 **다음** 별도 SQL로 DB 시각을 읽어 `accepted_at`으로 정한다. `accepted_at`이 판매 마감 전인지, 요청의 일정 버전이 현재와 같은지 확인한다. 잠금을 기다리기 시작한 시각을 쓰면 마감 뒤에 저장될 수 있기 때문이다.
8. 귀속 버전과 추천 이력을 다시 확인한다. 그 사이 다른 경로로 조합이 쓰였으면 rollback하고 5단계부터 다시 한다.
9. 한 트랜잭션으로 저장한다. 추천 요청(생성 방식, 필터 버전 포함), 5세트, 추천 이력, 기록 생성 또는 기존 기록에 추천 표시, 사용량 사건, 후속 job, 명령 결과.
10. 이미 직접 구매 등록한 조합이 추천으로 나오면, 기존 기록에 추천 표시만 추가한다. 구매 수는 늘지 않는다.

실패하면 아무것도 저장하지 않고 성공 사용량도 늘지 않는다.

## 3. 구매 등록과 취소

**등록**

1. 입력 전체를 검증하고, 요청 안의 같은 조합을 하나로 합친다.
2. 주체를 잠그고 같은 조합의 기록을 찾는다.
3. 없으면 만들고(CREATED), 추천만 받은 기록이면 구매 표시를 붙이고(CONVERTED), 이미 구매 등록이면 그대로 둔다(ALREADY_REGISTERED).
4. 사용량 사건을 같은 트랜잭션에 저장한다. 결과가 이미 게시된 회차면 같은 트랜잭션에서 판정 job을 등록한다.

**취소**

1. 화면이 본 기록 버전(`expectedVersion`)을 함께 보낸다. 다르면 충돌로 알리고 다시 조회하게 한다.
2. 추천 이력이 있으면 구매 표시만 해제한다. 없으면 `deleted_at`으로 숨기고 정리 대상으로 둔다.
3. 같은 취소 요청을 다시 보내면 번호 없는 완료 증명만 돌려준다. 그 사이 다시 구매 등록했어도 옛 취소 요청이 새 구매를 취소하지 않는다. 완료 기록 확인은 버전 검사보다 먼저 하고, 인증과 소유권 검사는 그보다 먼저 한다.

## 4. 비회원 귀속과 가져오기

1. 로그인은 귀속과 분리한다. 가져오기가 실패해도 로그인은 성공한다.
2. 유효한 비회원 자격이 있으면 비회원 주체와 회원 주체를 ID 순서로 잠그고 귀속을 만든다. 이미 다른 계정에 귀속됐으면 귀속하지 않는다.
3. 귀속이 끝나 이력을 일관되게 읽을 수 있게 되면 추천을 다시 허용한다. 그 전에는 새 추천만 잠시 막고 조회와 로그인은 유지한다.
4. 사용자가 "가져오기"를 확인하면 job이 기록을 묶음 단위로 옮긴다. 로그인 때 거절했거나 실패했으면 나중에 내 기록 화면에서 같은 API로 다시 시작한다(D-036). 귀속만 된 비회원 기록이 남아 있는 동안 이 진입점을 보여 준다. 같은 조합은 합치고, 사용자가 지운 대상은 건너뛴다. 항목마다 결과를 `history_import_item`에 남긴다.
5. 가져온 기록 중 결과가 이미 게시된 회차의 기록은 가져오기 job이 판정 작업을 등록한다. 주기적 미평가 대조([07 1](07-operations.md#1-작업-일정))가 가져온 기록의 회차를 덮으므로, 등록이 빠져도 다음 대조에서 판정된다 **[미확인]**.
6. 가져온 기록은 웹에서 판정하지만, 판매 마감 뒤에 가져왔다면 그 회차의 기본 알림 대상을 늘리지 않는다. 가져오기 결과에 그런 회차 목록을 담아 화면이 알린다([02 7.1](02-policies.md#71-비회원)).

## 5. 회차 마감과 알림 대상

1. 판매 마감 시각이 지나면 마감 worker가 회차 행을 배타 잠금한다. 진행 중인 저장이 끝나기를 기다린 뒤 회차를 봉인(SEALED)하고, 그때의 판매 마감 시각을 `cutoff_close_at`에 고정한다. 이 트랜잭션에서는 주체나 기록을 잠그지 않는다.
2. 알림 대상은 따로 저장하지 않고 기록의 시각으로 정한다(D-040). 회원 주체의 기록 가운데 `created_at < cutoff_close_at`이고 지워지지 않은(`deleted_at IS NULL`) 기록이 후보다. 그중 아래에 해당하면 대상이다.
   - 구매 번호: `purchased = 1`이고 `purchased_at < cutoff_close_at`. 1~5등을 알린다.
   - 추천 번호: `recommended_at`이 있다. 1~3등을 알린다.
3. 구매 등록을 취소하면 `purchased_at`이 비워진다. 그래서 마감 전 등록을 마감 뒤 취소하고 다시 등록하면 `purchased_at`이 마감 뒤가 되어 늦은 등록이다(D-041).
4. 가져온 기록은 회원 쪽 행이 생긴 시각이 `created_at`이다. 그래서 마감 뒤에 가져온 기록은 대상이 아니다([02 7.1](02-policies.md#71-비회원)). 마감 뒤에 가입한 회원도 마감 전 기록이 없으므로 대상이 아니다.
5. `created_at`, `purchased_at`, `recommended_at`은 서버가 DB 시각으로 찍는다. 화면이나 요청이 보낸 시각은 쓰지 않는다.
6. 서버가 마감 시각에 꺼져 있었어도 같은 규칙으로 정해진다. 마감 시점 상태를 따로 되살릴 필요가 없다.
7. 이미 봉인된 회차의 일정이 나중에 정정돼도 `cutoff_close_at`을 쓰므로 대상이 소급해 넓어지지 않는다. 운영자가 영향을 검토하고 그 회차 신규 발송을 멈출 수 있다.

## 6. 결과 수집과 게시

1. 수집 job이 결과 API를 호출한다. 일정은 [07 1](07-operations.md#1-작업-일정)에 있다.
2. 응답의 크기, 회차, 번호 범위, 중복, 보너스를 검증한다.
3. 짧은 게시 트랜잭션에서 회차만 잠근다.
   - 처음 받은 결과면 게시본 1을 만들고 `published_result_id`를 바꾼다. `published_result_id`가 바뀔 때마다 `publication_version`을 1 올린다.
   - 이미 게시한 결과와 의미가 같으면 새 게시본을 만들지 않는다. 게시본이 직접 등록한 결과면 `api_confirmed_at`만 채운다.
   - 의미가 다르면 격리(QUARANTINED)하고 운영자에게 알린다. 운영자가 현재 게시 버전과 사유를 넣고 승인하면 새 게시본이 된다.
   - 이미 격리한 결과와 의미(`semantic_hash`)가 같으면 새 행과 운영자 알림을 만들지 않고 받은 시각(`fetched_at`)만 갱신한다.
4. 게시 트랜잭션에서 판정 job과 과거 1등 목록 갱신 job을 함께 등록한다([03 4](03-architecture.md#4-비동기-처리)).
5. 등수별 금액이 아직 없으면 NULL로 두고 나중에 채운다. 금액만 채워지는 것은 새 게시본이 아니다.

**직접 등록(D-034)**

1. ADMIN이 관리자 화면에서 회차, 번호, 보너스, 사유를 넣는다. 화면은 번호를 두 번 입력받아 같을 때만 보낸다.
2. 서버는 권한, 최근 5분 재인증, 화면이 본 `publication_version`을 확인한다. 그 회차에 게시된 결과가 있거나 추첨 시각 전이면 거부한다.
3. API 결과와 같은 검증(번호 범위, 중복, 보너스)을 거친다. 3단계의 게시 트랜잭션과 같이 회차를 잠근 뒤 `source=MANUAL`인 게시본을 만든다. 그 사이 자동 수집이 먼저 게시했으면 거부한다. 이후 판정과 알림은 4~5단계와 같다.
4. 감사 기록에 등록한 값과 사유를 남기고, 운영자 알림으로 "직접 등록됨"을 알린다.
5. 그 뒤에도 결과 수집은 계속한다. 같은 결과가 오면 3단계의 둘째 경우, 다른 결과가 오면 격리 경우로 처리한다.

## 7. 판정

1. 판정 job은 게시본별로 기록을 ID 순서로 묶음 처리한다. 묶음마다 lease 토큰과 진행 위치를 검사한다.
2. 기록별 판정은 게시본과 기록 버전을 함께 저장한다. 판정 중 기록이 바뀌었으면 다시 판정한다.
3. 새 게시본이 나오면 이전 게시본의 판정 job에 취소를 요청하고(`cancel_requested`) 새 게시본의 판정 job을 등록한다. 판정 job의 중복 키는 게시본 ID다.
4. 결과 게시와 늦은 입력이 엇갈려 빠진 기록은 개별 사건과 주기적 미평가 대조로 판정한다.
5. 최신 판정 전까지 화면은 "확인 중"이다. 이전 게시본의 등수를 현재 등수로 보여주지 않는다.

## 8. 알림 발송

### 8.1 메시지 상태

| 상태 | 뜻 |
|---|---|
| PENDING | 보낼 준비가 됨 |
| IN_FLIGHT | 제공자 호출을 시작함 |
| ACCEPTED | 제공자가 접수함 |
| DELIVERED | 사용자에게 전달됨 |
| RETRY_WAIT | 제공자가 받지 않은 것이 확실함. 다음 슬롯에 다시 시도 |
| UNKNOWN | 접수 여부를 모름. 다시 보내지 않고 대조 |
| HALTED | 마지막 슬롯까지 실패해 자동 발송을 끝냄. 수동 다시 보내기 대상 |
| SUPPRESSED | 보내기 직전 확인에서 자격이 없어짐(취소, 동의 철회, 탈퇴) |
| EXPIRED | 유효기간이 지남 |
| FAILED | 복구할 수 없는 오류. 운영자 대조 대상 |

정상 순서는 PENDING → IN_FLIGHT → ACCEPTED → DELIVERED다. 늦게 받은 조회 결과가 DELIVERED를 ACCEPTED로 되돌리지 않는다.

### 8.2 슬롯 실행

슬롯마다 job 하나가 돈다. job의 중복 키는 (회차, 슬롯 시각)이다.

1. 회차에 게시된 결과가 있는지 본다. 없으면 수집을 한 번 시도한다. 그래도 없으면 이 슬롯은 실패이고 원인은 "미발표" 또는 "결과 API 오류"다.
2. 알림 대상 기록(5절)의 판정이 최신 게시본 기준으로 끝났는지 본다. 이전 게시본과 새 게시본의 판정이 섞여 있으면 이 슬롯에서 새 메시지를 만들지 않고 원인을 `EVALUATION_PENDING`으로 남긴다.
3. 대상 기록이 있는데 아직 결과 알림 메시지가 없는 회원에게 메시지를 만든다. 회원당 요약 1건이다. `delivery_message`의 (회원, 회차) 유일 제약으로 두 번 생기지 않는다. 대상이 없는 회원에게는 만들지 않는다.
4. 메시지마다 보내기 직전에 현재 소유, 동의, 구매 상태, 최신 결과를 다시 확인한다. 자격이 없어졌으면 SUPPRESSED. 아직 한 번도 호출하지 않은 메시지(`attempt_count = 0`)는 최신 게시본으로 본문을 다시 만든다.
5. 연락처·동의 버전, 실제 본문, 템플릿 버전, 수신자를 암호화한 사본으로 고정한다. 다시 시도할 때 같은 요청 키의 본문이나 수신자를 바꾸지 않는다.
6. 월 예산 카운터를 조건부로 늘려 비용을 예약하고(8.4), 비용 상태 RESERVED, 시도 수 증가, IN_FLIGHT를 같은 트랜잭션에서 커밋한 뒤 트랜잭션 밖에서 제공자를 호출한다. 요청 키는 `customFields`에 넣는다.
7. 응답에 따라 ACCEPTED 또는 RETRY_WAIT로 바꾸고, 제공자 메시지 ID와 마지막 오류 코드를 메시지에 남긴다. 응답이 없거나 서버가 중간에 꺼졌으면 UNKNOWN이다. 예산 카운터도 같은 트랜잭션에서 바꾼다(8.4).
8. 슬롯 결과를 job에 남긴다. 성공, 또는 실패와 원인 코드, 실패 건수다. 운영자 알림 대상 슬롯이면 운영자 알림 job을 만든다.
9. 마지막 슬롯(다음 날 12:00)이 실패하면 남은 PENDING과 RETRY_WAIT 메시지를 HALTED로 바꾼다.

한 회원의 오류가 다른 회원의 발송을 막지 않는다.

### 8.3 접수 여부를 모를 때

- lease가 만료됐다고 다른 worker가 IN_FLIGHT 메시지를 새로 호출하지 않는다. 멈췄던 원래 worker가 뒤늦게 호출할 수 있기 때문이다. job 회수([03 4](03-architecture.md#4-비동기-처리)) 때 그 job에 속한 IN_FLIGHT 메시지를 UNKNOWN으로 바꾸고, 비용 상태는 RESERVED로 둔 채 대조 대상에 넣는다. 원래 worker의 늦은 저장은 lease 토큰 검사로 거부된다.
- 대조는 인증된 제공자 메시지 조회로 한다(C-27). 제공자 메시지 ID가 있으면 그것으로, 없으면 수신 번호와 호출 시각 범위로 조회해 `customFields`의 요청 키로 맞춘다. 조회는 제공자 사용량 제한(5초에 20회) 안에서 나눠 한다. 콜백은 받지 않는다. 조회를 쓸 수 없으면 출시 조건을 채우지 못한 것이다.
- 제공자 조회가 일시적으로 "없음"을 돌려줘도 그것만으로 미접수로 확정하지 않는다.
- 제공자가 같은 요청 키의 중복 접수를 막아 준다는 사실이 확인되지 않으면, 이전 호출이 끝났고 미접수라는 것이 확정되기 전에는 다시 보내지 않는다.
- 조회 결과가 늦거나 순서가 바뀌어 와도 상태를 뒤로 돌리지 않는다(8.1).
- 정해진 기간([02 6.2](02-policies.md#62-발송-시각과-재시도)) 동안 확정하지 못하면 FAILED로 끝내고, 비용 상태를 확정 사용(SPENT)으로 바꾸고, 운영자에게 알린다. 그 뒤 조회에서 접수로 나와도 상태만 기록하고 다시 보내지 않는다.

### 8.4 예산

- 비용은 메시지마다 `cost_units`, `budget_month`, `cost_state`로 두고, 월 합계는 `message_budget` 한 행의 카운터로 둔다. 둘은 같은 트랜잭션에서 바꾼다.
- 예약은 조건부 증가로 한다. 예를 들어 `UPDATE message_budget SET reserved_units = reserved_units + ? WHERE provider = ? AND business_month = ? AND reserved_units + spent_units + ? <= ?`에서 바뀐 행이 없으면 예산 부족이다. 기본 알림의 상한은 인증용으로 남겨 둔 10%를 뺀 값이다([02 6.5](02-policies.md#65-비용)).
- 메시지가 IN_FLIGHT가 되면 예약한다(RESERVED). 접수되면 확정 사용으로 옮긴다(SPENT). 확정 미접수(RETRY_WAIT)이거나 제공자가 확실히 거절해 FAILED면 예약을 돌려준다(RELEASED). UNKNOWN은 예약 그대로 두고(확인 중 비용), 대조 기간 안에 확정하지 못해 FAILED로 끝나면 확정 사용으로 옮긴다.
- 지난달의 확인 중 비용은 지난달에 남긴다. 다음 달로 옮기지 않는다. 확정 미접수만 새 달 예산으로 다시 예약한다.
- 카운터는 메시지의 비용 상태 합계로 다시 계산할 수 있다. 정리 worker가 달마다 둘을 대조하고, 다르면 운영자에게 알린다.
- 금액은 0.1원 단위 정수로 관리하고, 제공자 청구와 대조한다.

### 8.5 결과가 정정됐을 때

정정 알림은 후속 기능이다([09 2.10](09-later-features.md#210-결과-정정-알림), D-042). 첫 출시는 아래까지만 한다.

1. 새 게시본이 나오면 7절대로 다시 판정한다. 화면은 최신 판정을 보여 준다.
2. 아직 한 번도 호출하지 않은 메시지는 보내기 직전에 최신 게시본으로 본문을 다시 만든다(8.2의 4). 이미 호출했거나 접수·전달·확인 중인 메시지는 다시 보내지 않는다.
3. 정정으로 새로 대상 등수가 된 기록이 있는데 그 회원에게 아직 메시지가 없으면, 자동 슬롯 기간 안에는 다음 슬롯이 만든다(8.2의 3). 그 뒤에는 수동 다시 보내기(8.6)로 보낸다.
4. 판정이 끝나면 운영자 알림을 보낸다. 이미 접수·전달된 메시지의 안내 요약(`communicated_summary`)과 새 판정을 비교해 "등수나 금액이 바뀐 회원 수"와 "새로 대상이 된 회원 수"를 넣는다. 번호와 회원 ID는 넣지 않는다.
5. 금액이 "확인 중"에서 확정된 것은 정정이 아니다. 화면만 갱신한다.

### 8.6 수동 다시 보내기

1. 운영자가 관리자 화면에서 회차를 골라 "다시 보내기"를 누른다. 사유를 함께 넣는다.
2. 서버는 권한, 다중 요소 인증, 가능 기간([02 6.2](02-policies.md#62-발송-시각과-재시도))을 확인하고 감사 기록을 남긴다.
3. 슬롯 실행과 같은 절차를 한 번 돈다. HALTED와 RETRY_WAIT 메시지를 PENDING으로 되돌린다. 대상 기록이 있는데 메시지가 없는 회원(정정으로 새로 대상이 된 회원 포함)에게는 새로 만든다.
4. ACCEPTED, DELIVERED, UNKNOWN 메시지와 SUPPRESSED 회원은 건드리지 않는다.
5. 결과는 운영자 알림과 관리자 화면에 남는다.

### 8.7 알림 계획 완료

회차의 알림 계획 완료 시각(`lotto_round.notification_plan_closed_at`)은 기록 삭제([04 6.1](04-data.md#61-기록-하나를-지울-때))의 전제다. 정리 worker가 아래 조건을 모두 확인하면 세운다 **[미확인]**.

1. 마지막 자동 슬롯(다음 날 12:00)이 끝났다.
2. 기본 알림의 수동 다시 보내기 기한([02 6.2](02-policies.md#62-발송-시각과-재시도))이 지났다.
3. 그 회차의 결과 알림 메시지가 모두 최종 상태다. PENDING, IN_FLIGHT, RETRY_WAIT, UNKNOWN이 없다. IN_FLIGHT는 job 회수 때 UNKNOWN이 되고, UNKNOWN은 8.3의 종결 규칙으로 끝난다.
4. 알림 대상 기록(5절)의 판정이 최신 게시본 기준으로 끝났다.

한 번 세운 시각은 되돌리지 않는다. 그 뒤에 정정이 생기면 판정과 화면만 갱신하고 운영자에게 알린다(8.5). 새 메시지는 만들지 않는다.

### 8.8 인증 코드

- 인증 코드는 회차와 상관없이 인증 목적의 메시지(`round_no` 없음)로 바로 보낸다. 결과 알림의 발송 슬롯과 유효기간을 적용하지 않는다.
- 6자리 코드는 암호학적 난수로 만들고, DB 밖 키로 만든 HMAC(요청 ID, 목적, 대상, 코드)으로만 저장한다. 키 버전을 함께 둔다.
- 요청 행을 잠근 상태에서 시도 수 증가, 기한 확인, 사용 여부 확인, 인증 버전 전환을 한 번에 처리한다. 다시 발급하면 이전 요청은 무효가 된다.
- 코드 본문은 사용이 끝나거나 만료되면 바로 지운다. 대조용으로 코드 없는 메시지 ID와 비용 상태만 남긴다.

## 9. 집계

1. 추천, 구매 등록, 조회 같은 활동이 성공하면 같은 트랜잭션에 사용량 사건을 저장한다.
2. 집계 job이 기간 단위로 원천 사건에서 다시 계산해 `usage_aggregate`를 덮어쓴다. 같은 job을 다시 돌려도 결과가 같다(C-28). 고유 이용자는 그 기간 사건의 서로 다른 주체 수로 센다.
3. 하루, 한 달, 한 회차가 끝나고 보정 기간([02 9](02-policies.md#9-통계))이 지나면 원천과 대조해 그 기간 집계를 VERIFIED로 확정한다.
4. 확정된 범위만 원천 정리가 가능하다.

## 10. 보관 정리

정리 worker가 [07 1](07-operations.md#1-작업-일정)의 일정대로 보관 기간이 지난 기록을 찾아 [04 5](04-data.md#5-보관-정리)의 보호 조건을 확인하고, [04 6.1](04-data.md#61-기록-하나를-지울-때) 순서로 지운다. 비회원 정리는 [04 6.3](04-data.md#63-비회원을-정리할-때)을 따른다.

## 11. 탈퇴와 재가입

1. 최근 5분 안에 재인증한 회원이 탈퇴를 요청한다.
2. 주체를 잠그고 접근 차단을 커밋한다. 응답은 "삭제 접수"이고, 삭제가 끝나기 전에는 완료로 표시하지 않는다.
3. 삭제 job이 [04 6.2](04-data.md#62-탈퇴할-때) 순서로 지우고 진행 위치를 job에 남긴다. 뒤늦게 도착한 가져오기, 판정, 발송, 제공자 조회 결과는 주체 상태를 다시 보고 멈춘다.
4. 같은 소셜 계정으로 다시 로그인하면 소셜 계정 연결이 없으므로 새 회원과 새 주체가 생긴다.

## 12. 복원

백업 복원 때는 [04 9](04-data.md#9-삭제-기록과-복원)의 규칙과 [07 4](07-operations.md#4-백업과-복원)의 절차를 따른다. 핵심은 최신 삭제 기록을 다시 적용하기 전에는 서비스를 열지 않는 것이다.
